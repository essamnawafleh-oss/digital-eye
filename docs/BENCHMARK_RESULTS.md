# Benchmark Results — PaddleOCR path (2026-10-24)

> **Synthetic data only.** All documents were generated by
> `benchmarks/make_synthetic_dataset.py`: one font (DejaVu Sans), printed text,
> simulated scanner defects. Real scans (other fonts, stamps, photos, handwriting,
> faded paper) are expected to be harder. These numbers do **not** describe accuracy on
> real documents.

## Setup

- Hardware: 4 vCPU (x86_64), 15 GB RAM, no GPU, Linux.
- Software: Python 3.13.16, paddlepaddle 3.3.1 (CPU, oneDNN off), paddleocr 3.7.0.
- Models: `PP-OCRv5_mobile_det`, `arabic_PP-OCRv5_mobile_rec`, `en_PP-OCRv5_mobile_rec` (cross-check).
- Options: `{"vlm": {"enabled": false}, "strict_network_guard": true}`, so level 3 is off.
- Each set has 45 documents: 36 building permits (12 Arabic, 12 English, 12 mixed) and
  9 coordinate tables, at three quality levels (clean; mild: 0.6° skew, light blur/noise,
  JPEG 70; heavy: 1.5° skew, blur 1.1, noise 18, JPEG 40). Inputs are PNG, JPEG and
  image-only PDF. Values (names, numbers, dates) are random per set.

## Development history (why three sets)

| Set (seed) | Role | Status |
|---|---|---|
| A (2026) | Rules were developed by looking at its errors | seen |
| B (99) | Used to check the first fixes; then its errors were also studied | seen |
| **C (31337)** | Generated last, evaluated once with the final code, **not used for tuning** | **unseen**, the honest number |

False acceptance (a wrong value returned *without* a review flag) during development:

| Code version | Set A | Set B |
|---|---|---|
| First real OCR run | 5.8 % | — |
| + number/label fixes, review flags | 2.2 % | 3.1 % |
| + second recogniser cross-check, OCR-line segmentation (final) | 0.0 % | 0.0 % |

## Final results on the unseen set C

| Metric | Value | Meaning |
|---|---|---|
| Documents failed | 0 / 45 | |
| **False acceptance rate** | **0.44 %** (1 of 225 fields) | wrong value returned as trustworthy |
| Uncertainty detection | 97.1 % | wrong or missing values that were flagged |
| Field exact match | 84.4 % | fields correct and returned |
| Critical fields exact match | 72.2 % | permit number, plot number, area |
| Required-field coverage | 90.2 % | expected values returned as `extracted` |
| Unnecessary review rate | 12.6 % | correct values still flagged |
| Coordinate values within ±0.005 | 100 % (153/153) | all quality levels |
| Time per document | mean 4.6 s, p95 10.3 s | coordinate tables are the slow ones |
| Peak memory (process) | 1.25 GB RSS | includes all three models |

By language (set C, fields): English 60/60 correct; mixed 71 correct, 1 false acceptance;
**Arabic 38 correct, 34 flagged**. Most Arabic flags are deliberate. Every area written
in Arabic-Indic digits goes to review, because the model drops the decimal separator `٫`.
In practice, **Arabic documents currently need a human check for many fields.**

The one false acceptance on set C: the owner name `ليلى` was read with a Persian yeh
(`لیلى`, U+06CC), which looks the same on screen but is a different character. Letter-form
normalisation (Persian yeh/keheh → Arabic) was added **after** this run, so it is not
reflected in the 0.44 %. A new unseen set is needed to measure it.

## What this does not show

- Accuracy on real documents (none available yet).
- The vision model (level 3) — never run with weights.
- Handwriting, stamps, photos taken with a phone, multi-column layouts, drawings.

Reproduce:
```bash
python benchmarks/make_synthetic_dataset.py /tmp/set_c --n 12 --seed 31337
python benchmarks/evaluate.py /tmp/set_c --options opts.json --report report.md
```

# Update 2 — multiple fonts, merged readers, stronger-model evaluation (2026-10-24, later)

The results above used **one font (DejaVu Sans)**. With 8 open Arabic fonts (Amiri,
Cairo, Harmattan, Lateef, Noto Naskh Arabic, Noto Sans Arabic, Scheherazade New, Tajawal;
OFL licences, used only to generate test data) the picture is worse and more realistic.

## Line-level test (benchmarks/arabic_lines.py, unseen set, 180 lines, value read exactly)

| Reader | All | Arabic words | Arabic line + Latin value | Arabic-Indic numbers | Dates | Latin lines | Time/line |
|---|---|---|---|---|---|---|---|
| arabic_PP-OCRv5_mobile_rec alone | 32 % | 56 % | **0 %** | 6 % | 0 % | 100 % | 0.1 s |
| **Arabic + Latin model merged (now the default)** | **56 %** | 56 % | 67 % | 6 % | 50 % | 100 % | 0.2 s |

Finding: the Arabic model drops Latin/ASCII values from Arabic lines in 7 of 8 fonts
(even on clean images); the Latin model reads them. Arabic-Indic digits are read
correctly by neither.

Step 1 (image clean-up) on the same lines: upscaling, autocontrast, binarisation,
sharpening gave **no gain**; extra white padding made results much worse (31 % → 2 %).

## Stronger recognisers (48 hard lines, CPU)

| Model | Size | Licence | All | Arabic words | Arabic-Indic numbers | Time/line | RAM | Verdict |
|---|---|---|---|---|---|---|---|---|
| merged Paddle (default) | 20 MB | Apache-2.0 | 46 % | 67 % | 8 % | 0.2 s | ~1.2 GB | default |
| **PaddleOCR-VL 0.9B** | 2 GB | Apache-2.0 | **67 %** | **92 %** | 33 % | **15 s** | **~9 GB** | candidate for an optional "strong" mode on flagged fields only; hallucinates on heavy degradation (`14/14/13` for a date) |
| Qari-OCR v0.3 (Qwen2-VL-2B) | 4.1 GB | Apache-2.0 | 54 % | 75 % | **0 %** | 5 s | ~8 GB | **rejected**: invents values (`١٨/٠٣/٢٠١٦` → `2/11/2017`), reverses digits, adds HTML tags |

PaddleOCR-VL needs `paddleocr[doc-parser]` (separate venv recommended).
